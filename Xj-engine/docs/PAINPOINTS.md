# 痛点地图（Why）— 每条规则解决什么痛点

> 规则是药方，痛点是病历。本文件将引擎全部规则/机制映射到其解决的真实痛点，
> 每条痛点均出自项目实际事故与评估记录（rules 迁移台账 C1~C6 冲突裁定、
> etl_async_contract R1~R7 三轮修订、2026-08-03 chunk_id 统一改造、RAG-ETL 能力评估）。

## 一、入库前链路（分片 / 清洗 / 校验）——解决"脏、碎、乱、伪"

| 规则 | 解决的痛点（没有它会怎样） |
|---|---|
| 语义优先分片（max_token=1200 / overlap=200，结构保护） | **表格/代码块被拦腰切断**——向量化片段语义残缺，检索命中表格一半、代码一半，拼不出完整答案 |
| min_token=100 + merge_small_chunks | **碎屑 chunk 污染索引**——几十字残片也 embedding 入库，向量库膨胀、召回 Top-K 被碎片挤占 |
| 清洗 normalize 7 开关 + 冗余过滤 | **脏文本直接入库**——全角半角混杂、HTML 转义残留、连续重复行，embedding 把噪声当语义，同内容洗出不同向量 |
| 7 个受保护标记跳过冗余过滤 | **清洗误杀结构**——表格空行、代码缩进被"折叠空格/删空行"误删（清洗与结构保护打架，冲突裁定 C2 出处） |
| 13 格式白名单 + pdf 显式拦截（ISO-6） | **PDF 混入 general 链**——PDF 走另一资产线，混入会产生两套 chunk_id 体系、双写向量库（历史红线事故） |
| 魔数校验（docx/xlsx/pptx/doc/wps） | **改后缀伪装穿透白名单**——exe 改名 .docx 入库，parser 崩溃甚至带入恶意内容，白名单形同虚设 |
| absolute_max_mb=50 硬拦截 | **巨型文件打爆内存**——几百 MB 文件全量读入解析，OOM 拖垮整个消费进程 |
| csv 编码探测序（utf-8-sig→utf-8→gbk→gb2312） | **中文 CSV 乱码入库**——gbk 按 utf-8 解码直接乱码，乱码文本 embedding 后成为永远检索不到的死数据 |

## 二、chunk_id 与幂等——解决"重、胀、丢、卡"

| 规则 | 解决的痛点 |
|---|---|
| chunk_id 统一内容哈希 int64（2026-08-03 改造） | **改造前五套 ID 体系并存**：CHUNK_ID_PREFIX / parse_chunk_id / p{doc_num} / PDF-__ 各自为政，跨链无法关联，删除对账全靠 LIKE 模糊匹配 |
| merge_insert 同 ID 覆写 | **重试/重复上传向量库膨胀**——同文件传三次存三份向量，检索返回三条重复，存储成本线性翻倍 |
| 递增不递补 | **ID 复用串数据**——旧 chunk 删除后 ID 被复用，引用旧 ID 的缓存/会话读到完全无关内容 |
| MD5 去重 scope=tenant_id + force_reparse 防自杀 | **双痛点**：①同文件重复上传全链路重算（embed 90s 白烧）；②重试时去重把自己半成品判"重复"拒写，任务永远卡死 |
| Redis `etl:index:done` SET NX EX 7d | **MQ 重复投递重复消费**——at-least-once 下网络抖动重发，同一任务跑两遍 ETL，双重 embed 双重写库 |
| outbox 状态机 + reconcile 三方对账 | **写一半崩溃成幽灵数据**——向量写了账没记（孤儿）、账记了向量没写（缺失），无人发现越积越多；差集清零让"最终一致"可验收 |
| 断点续跑 step_cache | **长链路失败从头再来**——6 步链第 5 步挂，重跑从解析重新 embed，90s GPU 时间全浪费 |

## 三、meta 字段与文档重组——解决"拼不回、滤不了"

| 规则 | 解决的痛点 |
|---|---|
| meta 携带 id_meta / biz_tag / keywords | **检索结果无法过滤溯源**——命中 chunk 不知来自哪个租户/文件/业务，多租户数据混杂无法隔离 |
| parent_chunk_id 锚（2026-08-24 用户提案） | **找到一句话拼不回整文件**——命中片段孤立，无聚合键只能全表扫 |
| 重组契约 R3 连续性校验（gaps 显式上报） | **缺号静默跳拼**——中间 chunk 被删，拼接结果少一段却看似完整，"残缺但正常"比报错更危险 |
| R4 严格升序（禁字符串序） | **"10" 排到 "2" 前**——lexicographic 排序拼出段落错乱的文件 |
| reassembly 外部化（opt-in 契约，不进引擎） | **引擎契约面膨胀 + 双份存储**——重组做进引擎需物化拼接结果，写放大且绑架所有消费方口径 |

## 四、异常分类与异步化——全部出身真实事故（R1~R7 修订记录）

| 规则 | 解决的痛点（事故） |
|---|---|
| 主队列 TTL 90s → **1800000ms**（R1） | **任务静默丢失**——实测文档级 embed 就要 90s，消息没消费完过期进 DLQ，用户见"上传成功"却永远无索引，零报错 |
| embed 模块级锁串行化（R3） | **6 线程争抢 GPU 全员变慢**——consumer 并发 encode，MPS 争抢单批 90s 长尾，吞吐不升反降 |
| 水位 503 → 入口零拒载（R5） | **高峰期用户被 503 弹回**——队列满即拒收，文件传完被告知失败；改 MQ 无界缓冲 + 告警代替报错 |
| reconciler 巡检补发（R6，300s） | **发布失败漏发成死单**——publish 抖动失败，任务停在 queued 永不被消费 |
| DLQ 永久保留卡死样本 | **毒消息反复炸 consumer**——畸形文件致消费崩溃循环重试堵死队列；DLQ 隔离 + 留样人工分析 |
| 三分类异常（resource/content/business） | **一刀切重试浪费资源**——文件损坏也重试 3 次白烧 embed；加密文件重试一万次也不会成功 |
| BM25 重建节流（60s 且 <10 篇跳过） | **每入一篇全量重建**——批量导 100 篇重建 100 次，I/O 打满入库雪崩 |
| Prometheus 告警三件套（R7） | **积压/DLQ 增长无感知**——consumer 停摆数小时无人知，用户侧只表现为"索引一直没好" |

## 五、规则外置化——解决"双写漂移、审计失明"

| 规则 | 解决的痛点 |
|---|---|
| 8 张 YAML 唯一真源（SSOT） | **C1~C6 六起双定义冲突**——白名单 constants.py 与 yaml 各一份且值不同，改一处漏一处，行为看运气 |
| 执行器禁写字面量 + RuleMissingError | **隐性默认值幻觉**——规则表缺的键代码悄悄硬编码兜底，审计无法发现实际生效值 |
| rules_loader 单入口（ISO-5） | **第二读取入口绕过治理**——执行器直接 open 规则表，缓存口径不一致，改规则不知谁在读 |
| isolation.yaml CI 机械断言（ISO-1~6） | **红线靠自觉守不住**——"general 禁碰 PDF 资产"无 CI 断言就是空话，一次疏忽即污染 |
| 台账编号溯源（表1-#N / 表2-HN / CN / TN） | **"为什么是这个值"三月后无人知**——1200/200/3×30s 无出处记录，想改不敢改 |

---

**痛点主线**：入库前解决「脏、碎、乱、伪」；写入时解决「重、胀、丢、卡」；写入后解决「拼不回、对不上、守不住」。
