# 五、工程技能规范（完整内容）

> 本文件正文实含 12 套技能规范（技能 1-12、14、15、21、22、24、25 中的 12 套有正文；技能 13、16-20、23、26-32 无正文）。全量 32 套技能（26 套原有 + 6 套 UI 设计体系）索引见 `01f_appendix.md` 工程技能调度总表。（2026-08-17 修复：原标题"共 32 套"与正文不符。）

## 技能1：需求澄清

**触发：** 需求模糊 / 想做个 / 大概是 / 我想要 / 能不能做

**第一步：** 复述问题让对方确认
「我理解你想做的是 [X]，目的是 [Y]，对吗？」确认之前不开始设计方案。

**第二步：** 提澄清问题（每次只问一个）
用户是谁？成功标准是什么？哪些在范围内/外？有什么约束？优先级怎么排？

**第三步：** 列出假设并确认
```
我目前的假设是：
- [假设1]
- [假设2]
→ 以上正确吗？有需要补充的吗？
```

**第四步：** 定义可测试成功标准
「更快」→「LCP < 2.5秒（4G网络）」
「好用」→「用户完成主流程步骤数 ≤ 3步」

**第五步：** 汇总确认后移交需求规格化

**完成检查：**
- [ ] 问题陈述已被确认
- [ ] 成功标准具体可测试
- [ ] 范围边界已定义
- [ ] 关键假设已确认

## 技能2：需求规格化

**触发：** 开始开发 / 写代码前 / 立项

**Spec 六要素（缺一不可）：**
1. **目标** — 做什么、为什么、用户是谁、成功是什么样子
2. **命令** — 完整可执行命令（含参数）
3. **项目结构** — 源码/测试/文档路径
4. **代码风格** — 一段真实代码示例
5. **测试策略** — 框架、覆盖率要求
6. **验收标准** — 可测试的完成条件

**四阶段门控（每阶段未确认不得推进）：**
```
澄清需求 → 制定计划 → 拆分任务 → 开始实现
```

**立即暴露假设：**
```
我目前的假设：
1. [假设1]
2. [假设2]
→ 请现在纠正我，否则按以上假设推进
```

**完成检查：**
- [ ] 六要素全部覆盖
- [ ] 关键假设已确认
- [ ] 验收标准具体可测试

## 技能4：切片实现

**触发：** 开始写代码 / 实现功能

**切片循环（严格按序，不可跳步）：**
```
1. 实现最小代码
2. 编写/更新测试
3. 运行测试——必须通过才能继续 【规范】
4. 提交代码
5. 进入下一个切片
```
测试未通过或代码未提交，禁止进入下一个切片。 【规范】

**功能开关（新功能必须使用）：** 【建议】
```javascript
if (featureFlags.isEnabled('new-feature')) {
  return newImplementation();
}
return legacyImplementation(); // 安全默认
```

**危险信号：**
- 未提交的改动横跨多个任务
- 「等功能全做完再写测试」
- 重构和功能开发混在同一次提交

**完成检查（每个切片）：**
- [ ] 全部测试通过
- [ ] 构建成功
- [ ] 改动已提交
- [ ] 当前状态可运行

## 技能8：接口设计

**触发：** 设计接口 / 定义API / 后端开发启动时

**原则：** 接口契约先于实现，先写文档再写代码

**统一错误格式：**
```json
{ "id": "1", "error": { "code": "PARAM_MISSING", "message": "参数缺失", "data": {} } }
```

**统一成功格式：**
```json
{ "id": "1", "result": { ... } }
```

**WebSocket / JSON-RPC 规范：**
```
请求：{ "id": "1", "method": "module.action", "params": { ... } }
成功：{ "id": "1", "result": { ... } }
错误：{ "id": "1", "error": { "code": -32600, "message": "..." } }
```

**必须显式覆盖的异常：**
参数缺失/类型错误 / 资源不存在 / 并发冲突 / 超时 / 权限不足

**完成检查：**
- [ ] 接口文档先于实现编写
- [ ] 错误格式统一
- [ ] 所有字段有类型定义
- [ ] 边界情况已定义

## 技能10：调试排错

**触发：** 有Bug / 报错了 / 排查问题 / 开发自测发现问题

**核心原则：** 证据驱动，禁止猜测，不理解原因就不修复 【建议】

**5步排错法：**
```
步骤1 观察
  读完整的错误消息（不是只看第一行）
  收集：错误信息 / 堆栈跟踪 / 复现步骤 / 环境信息

步骤2 稳定复现
  找到最小复现路径
  无法稳定复现时，先解决复现问题再排查

步骤3 缩小范围
  用二分法定位问题区域
  一次只改一处，观察变化

步骤4 假设与验证（一次一个假设）
  基于证据提出假设（最多3个）
  最小化实验验证
  结果与假设不符 → 修正假设重来

步骤5 修复与回归
  针对根因修复（不打补丁）
  添加测试防止回归
  确认修复不引入新问题
```

**禁止行为：**
- 不理解原因就修改代码
- 同时修改多处（无法定位哪处解决了问题）
- 把症状当根因
- 修完Bug不加回归测试

**完成检查：**
- [ ] 根因已确认（不是猜测）
- [ ] 修复针对根因（不是补丁）
- [ ] 已添加回归测试
- [ ] 修复不引入新问题

## 技能12：代码简化

**触发：** 重构 / 简化代码 / 减少复杂度（按需，任意阶段）

**核心模式：扩展-收缩安全迁移**
```
步骤1（扩展）：新旧并存
  新代码加进来，旧代码保持不动
  用功能开关控制切换

步骤2（切换）：逐步迁移
  把调用方一个一个切换到新代码
  每切换一个就测试

步骤3（收缩）：删除旧代码
  确认旧代码无调用后删除
  不提前删除
```

**禁止行为：**
- 一次性大范围重命名/重构
- 重构和功能开发混在同一次提交
- 在没有测试覆盖的情况下重构

**完成检查：**
- [ ] 重构前有测试覆盖
- [ ] 每步变更都有提交
- [ ] 行为未改变（测试仍通过）
- [ ] 旧代码已完全清除

## 技能15：Playwright UI自动化测试执行（Skill）

**触发：** Step5 测试用例设计完成后 / Step9 测试阶段 / Bug 修复后的回归验证

**技能文件：** playwright-test/SKILL.md（原 user/ 历史副本已随镜像目录于 2026-08-22 归档至 ~/.agents/archive/skills_user_mirror_20260822/，规则层不再引用该路径，见 00 唯一真源声明）

**口径标注（2026-08-13）：** UI 用例单源为 `ui-test-engineer` 产出的 cases.json，`.spec.ts` 由 `spec-emitter` 编译生成；本节手写 spec 路径仅适用于调试与既有项目维护，新项目禁止手写 spec 绕过单源。 【规范】

**调用方式（直接 Bash，不经过 MCP）：**

| 模式 | 命令 | 用途 |
|------|------|------|
| 全量批次 | `npx playwright test` | 150+用例，单浏览器单窗口 |
| 冒烟测试 | `npx playwright test --grep "SMOKE"` | 仅 P0 冒烟（5-8个）|
| 独立 spec | `npx playwright test tests/specs/surface/xxx-modal.spec.ts` | 调试表层交互弹窗 spec |
| 独立 spec | `npx playwright test tests/specs/data-link/config-calc-link.spec.ts` | 调试配置计算链路 spec |
| 过滤模块 | `npx playwright test --grep "CONFIG_CALC_LINK\|BASE_DATA_LINK"` | 按 describe 模块名过滤 |
| 过滤模块 | `npx playwright test --grep "SURFACE_INTERACTION"` | 仅表层交互模块 |
| 首失败即停 | `npx playwright test -x` | 快速排错 |
| 有头模式 | `npx playwright test --headed` | 肉眼观察浏览器行为 |

**定位方式说明：**
Playwright spec 使用标准 `element_description` 自然语言定位元素，不依赖 MCP Schema JSON。直接在测试代码中写 Playwright 原生 locator：

```typescript
test('TC-xxx: 描述', async ({ sharedPage }) => {
  await expect(sharedPage.locator('text=标题').first()).toBeVisible()
  await sharedPage.locator('button:has-text("确定")').click()
})
```

**Step 5 阶段 — 设计用例：**
1. test-case-designer 按分层隔离设计标准判定用例归属（surface/ 或 data-link/）
2. 按闭环模板设计完整用例，深度数据链路用例强制三层校验
3. 直接写 Playwright spec 文件到 `tests/specs/surface/` 或 `tests/specs/data-link/` 目录
4. 全量批次用例合并到 `run-all.spec.ts`（按 describe.serial 分组）
5. 表层交互 spec 禁止触碰 store 与持久化存储；数据链路 spec 禁止仅做表层 UI 操作 【建议】

**Step 9 阶段 — 执行用例：**
1. 确保应用已启动（自动 webServer 或手动 `npm run dev:web`）
2. 调用 playwright-test skill：`npx playwright test`
3. 查看结果：终端输出 + HTML 报告

**结果分流规则：**

| 结果 | 动作 | 下一步 |
|------|------|--------|
| 全部 PASS | 汇报项目经理「Playwright 全量测试通过」 | 自动进入 Step 11 |
| 有 FAILED | 记录 Bug（用例名/失败截图/日志），汇报项目经理 | 触发流程 B |
| TIMEOUT | 检查网络/服务器 → 重试一次 → 仍失败按 FAILED 处理 | 触发流程 B |

**交叉测试保留说明：**
- Skill 只接管 UI 层面（浏览器可见行为）的自动化执行
- 技术用例（TDD-xxx：接口测试、单元测试、逻辑验证）仍按原交叉测试规则由双方互换执行
- Skill 不能替代代码审查和人工判断，只加速 UI 回归测试

**完成检查：**
- [ ] UI 用例已按分层设计写入 surface/ 或 data-link/ 目录
- [ ] 深度数据链路用例已附带三层校验（视图/内存/持久化）
- [ ] 全量批次已合并到 run-all.spec.ts（按 describe.serial 分组）
- [ ] 测试报告已归档（含模块概览 moduleSummary）
- [ ] 失败用例已转为 Bug 记录
- [ ] 非 UI 用例交叉测试已完成
- [ ] 无只增不删的单向用例，全部新增有对应删除复原步骤

## 技能21：代码图谱分析

**触发：** 新项目初始化 / Bug精准回归 / 代码审查 / 用户说「分析」「生成」「使用」

**MCP Server：** `code-graph`（settings.json 已配置，`npx @sdsrs/code-graph serve`）

**核心命令（CLI 优先，Bash 直接调用）：**

| 命令 | 用途 | 调用场景 |
|------|------|---------|
| `code-graph-mcp incremental-index` | 建/更新索引 | 新项目启动、上传文件夹 |
| `code-graph-mcp map --compact` | 项目架构总览 | 了解代码结构前 |
| `code-graph-mcp impact <符号>` | 影响范围分析 | 改代码前评估破坏面 |
| `code-graph-mcp callgraph <符号>` | 调用图（callers/callees） | 追踪调用链 |
| `code-graph-mcp dead-code [路径]` | 死代码检测 | 代码审查 |
| `code-graph-mcp deps <文件>` | 文件级依赖图 | 了解模块依赖 |
| `code-graph-mcp overview <目录>` | 模块总览 | 快速了解模块结构 |
| `code-graph-mcp grep <模式>` | AST上下文搜索 | 替代普通 grep |
| `code-graph-mcp search <概念>` | 语义搜索 | 按功能概念找代码 |
| `code-graph-mcp refs <符号>` | 符号引用 | 查看引用/调用者 |
| `code-graph-mcp show <符号>` | 符号详情 | 看源码+签名 |

5. 遵守硬性约束：废弃权限/安全/性能场景，P0 核心数据流 ≥ 60%
6. 输出模块化测试报告，含四大模块通过率+耗时统计
