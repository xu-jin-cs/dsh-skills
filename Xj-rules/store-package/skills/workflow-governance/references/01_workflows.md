# 一、强制规则（最高优先级）

凡对话中出现以下任意触发词，必须立即执行对应流程，禁止跳过，禁止直接写代码： 【规范】

| 流程 | 触发词 |
|------|--------|
| 流程A：新增功能/项目开发 | `新增项目` `新增功能` `新功能` `我想做` `开始开发` `立项` |
| 流程B：Bug修复 | `bug` `Bug` `BUG` `报错` `异常` `崩溃` `修复` `不对` `出问题了` |
| 流程C：项目收尾 | `项目完成` `项目结束` `验收通过` `复盘` `结项` `完工` `交付` `收尾` `关闭` `搞定` |
| 流程D：代码图谱分析 | `分析` `生成` `使用` |
| 流程E：测试模式 | `测试` `执行测试` `跑测试` `测试一下` `做测试` `走测试` `进行测试` `开始测试` `跑用例` `执行用例` `回归测试` `冒烟测试` |

执行规则：
1. 由**项目经理**识别任务类型（新增功能 / Bug修复 / 项目收尾）
2. 项目经理完成角色指派与工程技能调度
3. 相关角色等待项目经理明确指派后才可开始执行
4. **增量优化202607**：PM/SPM/DPM/FE/BE 节点执行前自动触发 SV 前置审计，审计未通过（sv_verdict ≠ APPROVED）流程自动冻结，需修复对应项后重新提交审计
5. 每次任务完成后将经验写入对应角色的经验积累章节
6. **用户上传压缩包或给出项目路径时，PM 必须先校验项目前置输入 `.prd.md` + `.ui-proto.json`**，输入齐备后再开展后续工作（流程A Step1 硬性要求，其他流程也应按需执行） 【规范】
    - **前置输入判定禁止手写（2026-08-16 裁定，gate-switch 机械门禁）：** 「输入已齐备」禁止口头声称，必须扳动 `python3 ~/.agents/skills/gate-switch/scripts/gate_switch.py --spec ~/.agents/skills/gate-switch/specs/prd_inputs.json --set project=<项目根路径>` 照抄结论——判 A（`.prd.md` + `.ui-proto.json` 双存在）才允许开展后续工作；判 B 则 violations 原文即缺项清单，补齐后重新扳动。 【铁律】
7. **每次调用 Skill 时，第一行必须先输出技能名称声明**，格式：`[技能名称] — 用途说明` 【建议】
8. **目录树安全：** 详见 `00_root_safety.md`。本条仅作为交叉引用。
9. **新文件测试强制门禁（2026-07-07 新增）：** 新增核心文件（定义：≥50行逻辑代码）必须配不少于 3 个测试用例。测试用例必须覆盖主流程 + 异常 + 边界。零测试的新文件视为未完成，流程卡在当前节点不得推进。例外：纯配置/文档/脚本文件。 【规范】
10. **前端修改后构建产物验证（2026-07-09 新增）：** 涉及前端代码修改（.tsx/.ts/.jsx/.css 文件）时，PM 在汇报完成前必须确认以下自检： 【规范】
    - `npm run build` 成功（exit code 0，日志含 ✓ built）
    - dist/assets/ 下文件 mtime 已更新
    - grep 验证新增 UI 字符串在构建产物中存在
    违反视为 PM 失职。

11. **新文件导入验证门禁（2026-07-11 新增）：** 新增 Python 文件（≥50行）或新增导出函数（≥20行），提交前必须运行导入验证： 【规范】
    ```bash
    python3 -c "from <module> import <func>; print('OK')"
    ```
    验证通过后，再提交代码。PM 在步骤切换自检中确认此验证已执行。违反视为提交者失职。
    异常：纯配置/文档/脚本文件（无 import 路径）可跳过。
    **入口路径实测扩展（2026-08-12 新增）：** 改动触及入口/分发路径（CLI 包装脚本、main 函数、命令路由、模式分发）时，import 冒烟不足以证明存活——被改内部函数可能无任何按名导入方，import 通过 ≠ 运行期不 NameError。必须真实执行一次该入口的最小调用（如 `<wrapper> <最小参数>` 跑通一个模式分支）方可提交。 【规范】

12. **函数/文件重命名跨文件审计（2026-07-11 新增）：** 涉及函数重命名、类重命名、文件移动/重命名时，必须先 grep 全项目调用方再执行改名： 【规范】
    ```bash
    grep -rn "<old_name>" src/ app/ tests/ --include="*.py" --include="*.ts" --include="*.js"
    ```
    输出影响分析报告（列出所有引用文件、行号、调用方式），确认所有引用已同步更新后，再删除旧名称。
    违反视为重构事故，PM 负监督责任。
    - **改名零残留判定禁止手写（2026-08-16 裁定，gate-switch 机械门禁）：** 改名完成后「旧名已清干净」禁止口头声称，必须扳动 `python3 ~/.agents/skills/gate-switch/scripts/gate_switch.py --spec ~/.agents/skills/gate-switch/specs/zero_residual.json --set pattern=<旧名> --set "path=<项目源码目录>/**/*"` 照抄结论——判 A（旧名命中数==0）才允许宣告改名完成；判 B 则 violations 原文即残留实证，继续清理后重新扳动。（zero_residual 为一模三绑参数化模板，本处为「改名零残留」绑定；pattern 按正则解释，含特殊字符须转义。） 【铁律】

13. **新增依赖同步 requirements（2026-07-11 新增）：** pip install 引入新第三方库时，必须在同一操作中同步更新 requirements.txt。不得留待"下次一起整理"。BE 工程师在安装依赖后，PM 在步骤切换自检中确认 requirements.txt 已更新。 【规范】

14. **配置变更同步文档（2026-07-11 新增）：** 修改 config.py / 环境变量 / YAML/JSON 配置文件时，必须同步更新项目中的对应配置说明文档（README.md / config_summary.md / API 文档等）。PM 在步骤切换自检中增加"配置文档同步确认"项。禁止两阶段（先改代码再补文档），违反视为 PM 失职。 【规范】

15. **大需求 PM 四步强制顺序（2026-07-25 新增）：** 收到大型需求文档（明确为 L 档、多模块、角色权限、立项类）时，必须严格按以下顺序执行，禁止跳步、禁止先 spawn 子 Agent、禁止先做技术预研或局部修代码： 【规范】
    - **步骤 1：PM 声明流程** — 立即输出 `[技能声明]`，调用 `/pm` Skill，确认 `flow_type` / `size_gear` / `execution_mode`。
    - **步骤 2：输出 `pm_plan.json`** — 完成项目计划、角色指派、`next_steps` 定义，作为后续全部节点的上下文基线。
    - **步骤 3：`task_breakdown` 任务分片** — 调用架构师 Agent 输出分片规划（如 `task_slice_plan.json`），明确模块边界、依赖顺序与交付物。
    - **步骤 4：SPM 文档复盘学习** — 调用 SPM 输出 `learn-summary.md`，完成文档吸收与规范沉淀。
    四步全部完成后，方可进入 DPM 交互设计、UI 设计、FE/BE 开发等下游节点。违反视为 PM 流程合规失守。

16. **多 Agent 任务并行识别与执行规则（2026-07-25 新增）：** 架构任务分解（`task_breakdown`）完成后，PM 必须对子任务进行依赖关系判定，并据此选择串行或并行执行： 【规范】
    - **无上下依赖**（无数据、接口、状态先后依赖）的子任务 → 标记为 `parallel`，可并行执行。
    - **存在依赖**的子任务 → 标记为 `sequential`，必须串行等待前置交付物。 【规范】
    - 并行执行时按角色分组：多个 `frontend-development` Agent 可并行处理前端子任务；多个 `backend-engineer` Agent 可并行处理后端子任务；FE 与 BE 之间若接口契约已先行定义，可整体并行。
    - 每个并行 Agent 必须读取相同的上下文基线（`pm_plan.json` + `task_slice_plan.json` / `dev_task_breakdown.json` + `.prd.md` + `.ui-proto.json`），禁止各自为政。 【规范】
    - 并行结果必须通过 PM 节点统一合并校验（`merge_requirement` / 全域大纲完整性校验 / 冲突检测），确认无冲突后方可进入下游。 【规范】
    禁止在依赖关系未判明前盲目并行，禁止跳过合并校验直接推进。 【规范】

17. **SPM/DPM 后测试与开发并行执行规则（2026-07-25 新增）：** SPM 输出 PRD、DPM 输出详细交互设计后，测试用例设计、前端开发、后端开发可并行执行，将原串型链路改为并行链路：
    - **并行前提：** DPM 必须同时输出前后端接口契约（method / path / params / success response / error structure），作为 FE/BE/测试三方的共同基线。 【规范】
    - **后端引擎驱动：** 后端引擎识别 `ui-designer` 任务状态为 `COMPLETED` 且 `ui_spec.md` 已产出后，自动同时启动 `test-case-designer`、`frontend-development`、`backend-engineer` 三个顶层 Agent 并行执行；禁止 PM 模型手动串行指派。 【规范】
    - **并行组：**
      - `test-case-designer`：基于 `.prd.md` + `.ui-proto.json` + 接口契约设计测试用例。
      - `frontend-development`：基于 `.ui-proto.json` + 接口契约实现前端。
      - `backend-engineer`：基于 `.prd.md` + 接口契约实现后端。
    - **等待与执行测试：** 当 FE/BE 开发完成后，统一等待测试用例生成完毕，随后各角色执行各自测试：
      - 前端执行前端测试 / Playwright UI 用例。
      - 后端执行后端测试 / API 测试 / TDD 用例。
      - `test-executor` 执行 `test-case-designer` 设计的全量/冒烟用例。
    - **下游门禁：** 全部测试通过并产出测试报告后，方可进入 PM 确认、代码审查与冒烟测试节点。
    禁止 FE/BE 在接口契约未定稿前进入实现，禁止测试用例未生成前强行进入全量执行。 【规范】

18. **层级化多 Agent 并行分解规则（2026-07-25 新增）：** 在 UI 设计完成后，测试、前端、后端三个顶层 Agent 可并行启动；每个顶层 Agent 必须进一步调用 `task_breakdown` 架构任务分解生成 3 个子 Agent，实现最多 9 个 Agent 同层级并行执行： 【规范】
    - **触发条件：** `ui-designer` 输出视觉规范并通过 PM 确认后，进入层级化并行阶段。
    - **顶层并行组（3 个 Agent）：**
      - `test-case-designer`：接收 `.prd.md` + `.ui-proto.json` + 接口契约。
      - `frontend-development`：接收 `.ui-proto.json` + 视觉规范 + 接口契约。
      - `backend-engineer`：接收 `.prd.md` + 接口契约。
    - **子级并行分解（每个顶层 Agent 生成 3 个子 Agent）：**
      - 测试侧可拆为：表层交互测试、数据链路测试、API/TDD 测试。
      - 前端侧可拆为：租户生命周期页面、RBAC 权限页面、资源映射/配置页面。
      - 后端侧可拆为：租户生命周期 API、RBAC 权限与审计 API、网关/拦截/上下文。
    - **执行约束：**
      - 子 Agent 必须读取与父 Agent 完全相同的上下文基线，禁止子 Agent 自行扩展范围。 【规范】
      - 子 Agent 之间若无依赖则标记为 `parallel`；若有依赖则标记为 `sequential` 并由父 Agent 调度。
      - 父 Agent 负责收集 3 个子 Agent 的交付物并做内部合并校验，再向 PM 汇报。
      - PM 在三个顶层 Agent 全部汇报完成后，执行全域合并校验与冲突检测。
    - **规模控制：** 同一层级并行 Agent 数量建议不超过 9 个；超过时必须由 PM 显式审批并说明必要性。 【规范】
    禁止跳过顶层 Agent 直接 spawn 子 Agent，禁止子 Agent 绕过父 Agent 向 PM 直接汇报。 【规范】

19. **task_breakdown 后端引擎强制接入规则（2026-07-25 新增）：** 任务体量（S/M/L）判定由后端引擎执行；是否接入 `task_breakdown` 架构任务分解 Agent 由后端引擎控制，禁止模型自行跳过或关闭该节点。 【规范】
    - **S 档：** 原"可关闭分身并行、直接走单 Agent 串行"条款已废止（见 `09_governance_archive.md` 第十节）——S 档同样必须经 `task_breakdown` 拆解，允许拆解结果为 1 个分片的单 Agent 串行执行，禁止跳过拆解（有效条款见规则 22）。
    - **M/L 档：** 由后端引擎判定为中等或大型任务，必须接入 `task_breakdown` 生成 `task_slice_plan.json`，并根据规则 18/19/20 决定是否开启并行/层级化并行。 【规范】
    - **判定输入：** 后端引擎读取用户输入、`.prd.md`、历史项目规模等信号，输出 `size_gear` 与 `enable_task_breakdown` 标记。
    - **强制校验：** PM 节点在执行任何业务母体 Agent（spm/dpm/ui_designer/tcd/fe/be）前，必须检查 `task_slice_plan.json` 是否存在且有效；缺失时流程冻结并退回 PM 重新调度 `task_breakdown`。 【规范】

20. **任意 Agent 执行任务前必须调用 task_breakdown（2026-07-25 新增）：** 任何 Agent（spm/dpm/ui_designer/tcd/fe/be/test 等）被调用开始执行任务时，最高优先级步骤是调用 `task_breakdown` 架构任务分解 Agent 分解当前任务，然后 spawn 子 Agent 并行执行分片任务，最后由母体 Agent 整合结果。 【规范】
    - **适用范围：** 不论当前需求处于 S/M/L 哪个阶段，只要 Agent 被调用执行，就必须执行此步骤。（**与规则19原 S 档条款的冲突已裁决：本条为有效条款**，见 `~/.agents/logs/rule_conflict_adjudication.jsonl` 冲突①。） 【规范】
    - **执行顺序：**
      1. 接收任务指派与上下文基线。
      2. 调用 `task_breakdown` 生成分片规划（`task_slice_plan.json` 或角色级分片文件）。
      3. 根据依赖关系判定，无依赖的分片标记为 `parallel`，由子 Agent 同时执行。
      4. 子 Agent 完成后，母体 Agent 执行全域大纲完整性校验与合并。
      5. 产出统一交付物并向上汇报。
    - **规模适配：**
      - S 档：可拆分为 1-2 个子任务，子 Agent 数量≤2。
      - M 档：可拆分为 2-3 个子任务，子 Agent 数量≤3。
      - L 档：按规则 20 拆分为 3 个子 Agent，必要时形成 9-Agent 层级并行。
    禁止任何 Agent 跳过 task_breakdown 直接执行原始任务，禁止未做依赖判定就盲目并行，禁止子 Agent 绕过母体 Agent 直接汇报。 【规范】

21. **前端 UI 重构视觉合规抽检规则（2026-07-30 新增）：** 前端完成 UI 重构或视觉改版后，向 PM 汇报完成前必须执行视觉合规抽检： 【规范】
    - **必读输入：** `ui_spec.md`、DPM 交互设计、用户截图反馈（如有）。
    - **构建验证：** `npm run build` 通过，且 `dist/assets/` 中新增 CSS 类名与 UI 字符串经 `grep` 确认存在。
    - **随机抽检：** 至少抽查 3 处关键区域（如 Header 按钮、侧边栏条目、输入框提示、主按钮样式），核对布局、字体、颜色、间距、hover/选中态是否与规范一致。
    - **问题闭环：** 抽检发现任一不符立即修复并重新构建验证；未通过抽检禁止汇报完成。 【规范】
    违反视为 FE 自测失职，PM 不得推进到代码审查节点。

22. **M/L 档前端任务必须并行拆分规则（2026-07-30 新增）：** 判定为 M 档或 L 档的前端 UI 重构/视觉统一任务，PM 必须强制调用 `task_breakdown` 并 spawn 多个 FE 子 Agent 并行执行： 【规范】
    - **分片方向：** 布局骨架、组件拆分、样式 token/变量统一、交互状态、构建与视觉抽检。
    - **并行数量：** M 档拆分为 2-3 个子任务；L 档按规则 20 形成层级化并行。
    - **母体合并：** 子 Agent 完成后由母体 FE Agent 统一合并，执行冲突检测与视觉一致性校验。
    - **PM 门控：** PM 在步骤切换自检中确认 `task_slice_plan.json` 有效、并行执行记录存在、母体合并校验通过。
    禁止单一 FE Agent 独自承担整个 M/L 档前端重构任务。 【规范】

23. **批量编辑先汇总规则（2026-08-02 新增）：** 修改同类字段多处（≥3 处）时，必须先列「修改点归并表」再一次执行，禁止边改边发现。 【建议】
    - **归并方式：** 按字段类型分组（如所有 `next_agents` 一组、所有 `parallel` 一组、所有 `description` 一组），清点总数。
    - **执行选择：**
      - 修改点 >5 处且集中于一个文件 → 用 Write 全量重写。
      - 修改点分散在多文件/多独立位置 → 一条消息内并行发出多个 Edit。
    - **禁止：** "改一处→发现新处→再改"的螺旋模式，违反视为执行纪律缺陷。 【建议】
    来源：ppt flow.yml 拓扑修复项目，17 次串行 Edit 被用户两次提醒"为什么这么慢"。

24. **字段修改前验证消费规则（2026-08-02 新增）：** 修改任何配置/规则/YAML 字段前，必须先 `grep -rn "<field_name>" <引擎代码路径>/` 确认该字段被真实读取并影响行为，禁止凭字段名猜含义。 【规范】

33. **多任务生成即触发并行执行规则（2026-08-12 新增）：** 任何任务经 `task_breakdown` 分解后产生 **≥2 个子任务** 时，评估只是入口，**立即执行并行**才是目的；禁止只做评估报告而不触发实际并行。 【规范】

      - PM 在步骤切换自检中确认：`execution_topology` 存在、`parallel` 子任务已实际 spawn、合并校验已完成。

    - **零漂移对拍验证：** 机制上线前必须做「改动 → 恢复同内容」对拍：内容一致但 mtime/元数据变化时，检测结果必须为「无变更」。 【建议】
    - **三方向验收：** diff / 比对 / 同步类功能验收必须覆盖「新增 / 删除 / 修改」三个方向的最小用例。只验证插入方向等于没验（纯删除型编辑曾被 delete opcode 过滤吞噬，删除函数对影响面/测试选择/变更台账全部隐形）。 【规范】
    - **多层不一致追根因：** 两套独立检测机制（如行级快照 vs 内容指纹）结果不一致时是缺陷信号，必须追根因到口径对齐，禁止以「多跑一遍没坏」忽略。 【建议】
    来源：archmap lite 双模式 E2E 实证连续命中 retro-be-063（.pyc 致模块指纹永久误报）/ retro-be-064（纯删除变更隐形）。

35. **复盘规模分级规则（2026-08-13 新增）：** 用户触发 `复盘` / `结项` / `收尾` / `项目完成` 等流程C关键词时，PM 必须首先判定 retro 规模档位 `S/M/L`，再决定 retro 深度与交付物，禁止所有 retro 默认走完整 L 档流程： 【规范】
    - **S 档（轻量复盘）**：单点问题、1-2 个命令/文件可修复、无跨文件影响、无重复发生风险。处理：登记 `~/.agents/retro-registry/runtime/_retro_experiences_<project>.json`（按项目命名变体，如 `_retro_experiences_example.json`），输出 1-3 条落地动作，**不生成 retro skill、不走 5 问法**。
    - **M 档（标准复盘）**：涉及 3-5 个文件、存在同类复发风险、或需要形成可复用检查单。处理：登记 + 生成 retro skill + 简短根因分析，5 问法可压缩为 1-2 句。
    - **L 档（完整复盘）**：项目级收尾、反复出现的模式缺陷、涉及流程/规则/多角色协作。处理：完整四部分 + 5 问法 + 根因穿透链路 + GENERATE + skill/memory 落地。
    PM 必须在流程状态条中显式声明 `retro_size=S/M/L`。本次 claude CLI 入口缺失事件本应判定为 S 档，因未分级而走成 L 档，用户反馈“内容少、复盘久”。 【规范】
