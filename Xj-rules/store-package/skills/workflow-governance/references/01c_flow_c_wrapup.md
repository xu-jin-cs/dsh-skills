## 流程C：项目收尾

**步骤1** 项目经理向所有角色发出收尾指令。

**步骤2** 每个角色提交最短路径记录：
```
遇到的问题：[具体问题]
解决方案：[成功方案，失败的不记录]
以后如何避免：[预防建议]
适用场景：[哪类项目适用]
```

**步骤2.5** PM调用 retro-skill-dispatcher（GENERATE模式），扫描各角色经验，评估每条经验的可复用性：
- 可复用的经验 → 自动生成 retro SKILL.md 到 `~/.agents/retro-registry/skills/{id}/`
- 单次偶发的经验 → 仅记录到经验文档，不生成 SKILL.md
- 不生成 provenance.json（2026-08-16 用户裁定：provenance 字段删除——无消费方字段不存在的契约治理原则） 【规范】
- 注册到 registry-index.json（含 trigger_phrases、trigger_keywords、affected_role 等匹配字段）
- 详见 retro-skill-dispatcher/SKILL.md（`~/.agents/skills/retro-skill-dispatcher`）

**步骤3** 项目经理将记录写入各角色经验积累章节，并将可流程化的经验转化为配置变更（AGENTS.md 流程步骤/门禁规则/技能文件/通用规则）。只有不可流程化的经验才留存在经验文档中作为参考。转化原则：如果该教训能用 if/else/when 规则表达，就应该变成配置，而非笔记。

→ **技能生成 vs 配置变更严格区分（硬性）：**
- **生成/更新 SKILL.md（含 retro skill）** → 由 `retro-skill-dispatcher` GENERATE 自动投递，action 必须为 `SKILL_AUTO_GENERATE`，每条技能独立一条记录，details 使用 `generated_skills: [skill_id]`。禁止在此处手动发 `CONFIG_AUTO_APPLY` 掩盖技能生成。 【规范】
- **修改规则文件 / AGENTS.md / 记忆文件** → 才使用 `CONFIG_AUTO_APPLY`，details.changes 必须是字符串数组，每项格式 `"文件路径: 变更描述"`。 【规范】

**步骤3.5 — sv-supervisor 收尾复核门禁（2026-07-09 增强：新增第5层工程能力固化门禁）：**

PM 在提交 CLOSED 流转前，必须先完成以下交付物： 【规范】

1. **5问法复盘完整输出**：Q1（最成功决策）→ Q2（最失败决策）→ Q3（坚持什么）→ Q4（改变什么）→ Q5（体系缺陷），每问必须穿透三层： 【规范】
   - 从项目中总结（代码/架构/测试）
   - 从流程中总结（步骤合规/门禁/拦截）
   - 从对话中总结（沟通/验证/纠正）

2. **根因穿透链路**：从表层现象向上追溯至根因，标注每一层的修复状态（已修复/已打补丁/未修复）

3. **补丁分发清单**：每个根因对应的补丁写入哪个文件（AGENTS.md/SKILL.md/规则文件/经验文档），标注目标文件和改动人

4. **第5层工程能力固化清单（2026-07-09 新增）：** 逐项检查所有复盘结论，判定是否可工程化固化：
   - 命中第5层判定标准（可复用/可标准化/流程缺失/可自动执行/有固定交付物）的复盘结论 → 必须生成 Skill/Agent 【规范】
   - 已生成的 Skill/Agent → 检查闭环四件套齐备：调用闭环 ✓ / 流程规范 ✓ / 交付物 ✓ / Agent流转 ✓（仅Agent）
   - 不满足条件降级到低层的复盘结论 → 输出降级原因
   - **判定结论：第5层已固化通过 ✓ / 第5层不适用（无符合条件项）✓ / 第5层未完成 ✗**

以上四项交付物提交 sv-supervisor 审核：

```
【审批请求】收尾复核 | 提交方：PM
交付物：
  ✅ 5问法复盘（Q1-Q5，三层穿透）
  ✅ 根因穿透链路
  ✅ 补丁分发清单
  ✅ 第5层工程能力固化清单（判定结果+闭环四件套状态）
请求 sv-supervisor 裁决：通过/打回（注明缺失项）
```

sv-supervisor 审核标准：
- 5问法必须包含项目/流程/对话三层，任一层缺失 → 打回 【规范】
- 根因穿透链路必须有从表层到根因的完整链条，跳层/断层 → 打回 【规范】
- 补丁分发清单必须标注修改目标和状态，缺失 → 打回 【规范】
- **第5层固化清单必须逐项判定。存在可固化未固化项 → 打回。闭环四件套缺件 → 打回。** 【规范】
- 第5层清单完全不涉及 → 正常通过（适用于无工程化产出场景）
- （archmap diff 留痕审核项已废止，见 `09_governance_archive.md` 第十节第 3 条）

只有 sv_verdict=APPROVED 才允许进入步骤4（CLOSED）。不通过则 PM 补充缺失项后重新提交。


**步骤4** 输出《项目收尾总结》，项目正式关闭。
→ **最后校验：** 确认 sv-supervisor 步骤3.5 的审核结果为 APPROVED（未通过则关闭被阻止）。
